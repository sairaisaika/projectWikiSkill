# Portable hook declaration: source and host observations

The0.2.10 implementation was normally adopted: exact source and pull-request
matrices, then exact main matrices, passed on Windows/Linux Python3.10/3.13.
The source and main trees matched. One Windows host was updated through the
official plugin entry; the prior cache was backed up and hash-checked before
the update. Official inventory reported0.2.10 installed/enabled. Direct installed
doctor/source closure matched all25 payload files and preserved unverified
hook trust, execution, delivery, agent use and business acceptance.

A fresh read-only local app-server `hooks/list` then reported zero hooks for the
selected installed plugin, with no entry errors. Target plugin details likewise
contained an empty hook list. This is a real discovery gap, not evidence that an
untrusted hook ran or that user review was completed. Existing unrelated hook
trust and the active scoped engineering process were unchanged. No model turn,
new chat, trust mutation, hook bypass or application action was needed for this
observation. One initial metadata call supplied a directory where the protocol
expected the marketplace file; the corrected file-specific read succeeded.

The candidate adds the documented explicit OpenAI extension to the optional
portable root manifest. The canonical identity remains the source input; a named
`portable-openai-hooks-v1` projection binds the extra declaration. Doctor mirrors
that data transform, rejects a rehashed incorrect path or incompatible projection
and keeps legacy identity-only receipts valid. Plain packaging emits the original
canonical identity. No lifecycle, task-reader or host-trust logic changes.

Four focused cases on the previous source produced two controls passing, one
missing-declaration failure and one missing-extension error in a future-format
test. The new four cases pass, including tampered-path refusal and legacy format
compatibility. Whole-suite, exact final CI and normal adoption are separate gates.
The complete local suite then ran191 tests:189 passed and the same two Windows
unprivileged-symbolic-link cases skipped. The12 fixture behavior tests, declared
Wiki/navigation checks and diff check passed. The new doctor also inspected the
real installed0.2.10 package against its matching source: package/source/identity
remained valid under the legacy projection, with hook execution still unverified.

An independently scoped read-only reviewer checked all four selected source
hashes before and after reading. Data-only probes of the actual projection nodes
confirmed plain/portable and legacy schema1/schema2 cases, rejected wrong or
missing targets and invalid projection/profile combinations, and preserved
canonical identity plus unrelated extension fields. No Git, package commands,
tests or host operations ran in that review. Its narrow source closeout does not
certify installed discovery or make unsigned receipts authentic.

Read-only metadata probes for two **uninstalled** private packages (old and new)
both returned empty hook descriptions. A further private diagnostic variant with
an extra default-named hook file did too. Those artifacts were not installed,
trusted, added to host configuration or represented as valid canonical packages;
the extra-file variant was intentionally outside its original receipt. These
results do not establish the installed resolver's cause or prove this candidate
fixes runtime discovery. Retain that uncertainty until the normal installed
hook-list check is repeated. Do not ask a user to trust a hook that is not listed.

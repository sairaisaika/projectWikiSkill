# Selected-peer consumption and an unchanged review return, C70

This is a guided follow-up in a real coupled Web/native project. It is not a blind
trial, a measured speedup, full source coverage, host lifecycle verification or
business acceptance. Private repository identifiers, machine paths, session IDs,
account values, clinical content and raw operational logs are excluded.

## Why this follow-up was necessary

In the preceding review, a worker had accurate native context but consulted an
old convenient Web primary checkout. Its report labelled that reference; the
coordinator separately checked the current producer before adopting the finding.
Supplying an identity in a prompt did not establish that every source consumer
actually used it. The existing [source-selection evaluation](evidence-source-selection-c60-20261022.md)
already distinguishes selected inputs, transport and semantic claims. This case
applies that method at the worker's real reading/return seam rather than adding
another registry or claiming a new helper defect.

## What was actually exercised

1. The coordinator selected clean, detached Web and native Git snapshots. The
   Web snapshot matched the observed deployed source; the native snapshot was
   adopted source, explicitly separate from the installed application. Newer Wiki
   prose on a pending branch was not claimed present in the chosen Web snapshot.
2. The existing0.2.5 source `workflow.py` was copied for one private invocation.
   Its SHA256 matched the source byte-for-byte. This was not an installation,
   upgrade of the already-running worker's scoped0.2.4 plugin, hook, new controller
   or payload change. The original native router ran through the explicitly
   supplied runtime without downloading dependencies. Its observed runtime and
   source-peer metadata survived capture, start and read-only delegation.
3. The actual child packet had `access: read_only`, no allowed edit files, three
   required capabilities and six planned source files. Complete satellite counts,
   omitted candidates, declared runtime inputs and native finish rules survived.
   The index explicitly said it was not a full reading.
4. The reviewer reported reading the index, selected feature view and all six
   exact impact views, then relevant omitted-page sections directly. It named the
   selected Web/native snapshots and excluded the stale convenient primaries.
   Its consumed-source record distinguished full, partial and test-name-only
   reading. Missing authentication-library lock details stayed unavailable;
   the worker did not silently borrow a different implementation checkout.
5. The coordinator checked every reported source-file hash against the selected
   roots and independently confirmed both HEADs and clean Git states. These checks
   substantiate the selected bytes and unchanged return. They do not independently
   trace every physical read, prove every inference or detect transient reverted
   writes, ignored files and external state.
6. After the child stopped, the coordinator recaptured the actual unchanged
   source with no fabricated `--files`, generated the existing unreviewed review
   template, filled the evidence/gaps and ran the original `finish`. The actual
   result had empty `actual_files`, no structural issues and
   `structural_reconciliation: true`, while retaining the original-viewer
   capability explicitly in `capability_gaps`.

The source inventory is useful evidence, not proof that all satellites were read:
the reviewer explicitly left some omitted parent/whole-journey pages unreviewed.
Likewise, matching hashes do not turn reported read events into independently
observed tool telemetry. The private report and public summary retain these limits.

## Product finding and the separate implementation return

The bounded task reviewed a private task-list/completion UI and its real server
membership rule. A target-keyed UI window and account-root remount protected which
rows were displayed, but the caller had not opted into the existing API bridge's
original-viewer check. A completion awaiting authentication could therefore use
a different participant's credentials in a synthetic probe. Because the server
legitimately allowed either participant to change status, resource authorization
alone did not preserve who intended the action. No authored content crossed the
boundary; this was an attribution/integrity finding, not a demonstrated disclosure.

The reviewer used byte-identical source copies with mocked session, network and
server behavior. It did not mount React, execute the real authentication library
or reach a backend/device. Whether the same timing is reachable through the real
authentication library's locking remains unverified. Unrelated-participant denial,
read-only history, target-specific paging, uncertain-result pauses and a
practitioner retaining ordinary recipient capabilities were considered separately.

In a separate implementation tree, the coordinator then mounted the actual React
screen, original window model and original API bridge with synthetic session/fetch.
Six of nine cases failed before repair; nine of nine passed after reusing the
existing original-viewer option at this caller's two private request sites.
Positive controls retained ordinary/practitioner recipient behavior and legitimate
provider history. The candidate's full59 suites/738 tests, type check, original
single-source ratchet plus seven injected self-tests,31 artifact/source guards and
61 canonical source comparisons passed locally. Exact remote head/source adoption,
original Wiki adoption and device evidence remain distinct checkpoints.

That implementation did not edit the review's frozen sources, retrospectively
remove its capability gap or make the read-only packet an editing authorization.
It also corrected stale source comments about the server's default recipient
selection. Original-page corrections and remaining server-concurrency/caller/device
work belong to the existing native Wiki and debt owners, not a duplicate ledger.

## What this changes in the collaboration assessment

- Observed: real capture → read-only delegation → reported exact-view/source use →
  coordinator source/hash inspection → unchanged recapture → structured return
  retaining a real capability gap. A useful source finding led to a separately
  scoped component-level counterexample and repair candidate.
- Not established: every future worker choosing the correct peer, automatic hook
  trust/enforcement, a semantic certificate, independently traced reading,
  authentication/runtime reachability, business/device acceptance or efficiency.
- No package/version/reinstallation implication: the existing
  [collaboration workflow](../../project-wiki/references/collaboration-workflow.md)
  and [native adoption](../../project-wiki/references/native-wiki-adoption.md)
  already provide the required source-selection and return vocabulary. No helper,
  packaged reference, manifest, hook or runtime controller changed in this report.

The practical gap was consumption of an existing context contract. A valid
read-only return can preserve a feature gap while producing useful implementation
work; structural closure and feature completion remain separate conclusions.

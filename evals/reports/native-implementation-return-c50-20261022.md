## Return friction and actual recovery

A root integration start using an earlier context was rejected after source/wiki
bytes changed. The coordinator recaptured actual WIP rather than disabling the
freshness check. Those captures explicitly describe already-existing edits; they
are not retrospective claims that all edits began after the new packet.

The actual final file query included staged files, working changes and newly added
source/tests across both selected repositories. `git diff` without a base would
have missed staged files. Native deterministic line/function/delta extensions were
retained in the actual impact records; they were syntax facts, not semantic
coverage. The behavioral findings above did not originate from those counts, so
this case does not measure a benefit from file-size heuristics.

Final return preparation exposed previously unregistered locale and aggregation
consumers. Their exact declarations were routed through the original i18n page;
functional files were not dismissed as generic text. The first wiki return also
misplaced source-format entries outside source sections and guessed an export
keyword. The project's unchanged gates rejected those mistakes. Correcting their
actual placement/declarations, rather than weakening the gate, restored closure.
An attempted reader build during concurrent coordinator staging returned an input
change failure; a later immutable post-commit build succeeded. These were real
coordinator/tool-use failures, not product defects or synthetic success receipts.

The final prepared review distinguished source-verified capabilities from a
remaining user-experience/runtime gap. Post-commit reconciliation bound both
actual heads and retained the complete real diff. It passed structurally while
still naming missing device journeys, authoritative clock consumption, precise
notification context and full professional scheduling editors. It did not run or
certify project checks itself.

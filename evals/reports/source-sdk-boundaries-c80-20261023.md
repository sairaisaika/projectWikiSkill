## Source review is not compiled-runtime binding

The bounded question concerned native signup/login producers, CAPTCHA, SDK session
storage/events, navigation and returned-user consent tasks. UI lifetime guards
retired alerts/navigation but did not cancel an already-started SDK operation.
The source review identified two conditional gaps: late auth session writes and
late MFA decisions applying to another current session. Valid anonymous signup
and the original returned user's pending consent had to remain supported.

The separate dependency installation matched the selected lockfile's SDK version,
and its inspected source files were hashed. That still did not bind the built
package entry to the selected source tree, an application bundle or a device.
An exported lock utility or broad SDK field comment was not proof that the actual
signup/password method bodies used that lock. The report retained those limits.

The coordinator then ran the actual installed compiled SDK2.110.8 separately,
binding37 loaded compiled module hashes. All responses and storage were synthetic,
the default/unmatched network path was rejected, and no real credential, account,
backend configuration or device was used. PKCE and persistent storage were kept;
auto-refresh was disabled for deterministic isolation.

| Controlled observation | Actual result | Limit |
|---|---|---|
| Earlier signup returns a session after a later login completed | Stored/current session changed back to the earlier user | Requires a session-bearing response; not a claim about deployed email-confirmation policy |
| Earlier password login returns after a later login completed | Stored/current session changed back to the earlier user | SDK boundary only; no UI reachability or backend event proof |
| Earlier signup returns a confirmation-only user | Later login remained current | Retains the legitimate pending-user path |
| Ordinary signup returns its session without a competing login | Normal success remained | Does not establish real registration or legal consent |

These observations substantiate the source-supported conditional SDK finding.
They do not turn the read-only task into an editing authorization, a production
incident report or a complete authentication repair. In particular, restoring a
previous session or signing out the newer user was not used as compensation.

## Separate implementation and native Wiki return

In its owned implementation tree, the coordinator mounted the actual AuthProvider
with React and the real compiled SDK, synthetic fetch/storage and mocked policy,
CAPTCHA, push, consent and telemetry edges. Five of eight original cases failed:
old MFA decisions or flags affected another session, and a delayed empty boot read
replaced a newer auth event. The existing provider was repaired with a synchronous
session snapshot/revision and delayed-result ownership checks. Additional tests
covered late boot failure and a rejected-SDK logout fallback; that last case does
not establish safety of a successful in-flight SDK logout's own storage mutation.

Ten focused cases and61 suites/761 tests passed, with positive current-user MFA
controls, type checks, original source guards and exact source/main CI separately
verified. This bounded publication repair leaves the SDK session-write finding
open. No dependency/vendor patch, new auth store, API, backend policy, CAPTCHA,
returned-user consent contract, APK or device change was made.

The original Wiki's session mechanism and login consumer received the local
sequence, actual test/audit sources and open producer gap. A relevant role
satellite still said that no native calendar screen existed. Reading the actual
navigation/screen consumer disproved that statement; the existing original page
was corrected without claiming complete practitioner or device functionality.
Original native generators, source checks and the explicitly paired reader ran;
their green structure did not erase other recorded capability gaps.

## Reusable conclusion and remaining evaluation

The existing [collaboration workflow](../../project-wiki/references/collaboration-workflow.md)
and [native adoption](../../project-wiki/references/native-wiki-adoption.md) already
separate selected inputs, worker claims, actual diff, capability gaps and native
return. This case adds observed use of that method, not another source registry.
External dependency source, compiled entry, injected-runtime observation, deployed
policy and device bundle remain distinct evidence layers.

Observed: a real constrained context led to a source finding, separately bound SDK
counterexamples, a scoped provider repair and original-page consumer correction.
Unmeasured: locating time, baseline comparison, missed-link rate across future
tasks, complete hook trust/execution, independently traced reading, full semantic
correctness and business/device acceptance. Those remain requirements for wider
rollout; no efficiency or universal-agent adoption claim follows from this case.

# C22 live collaboration: implementation is not acceptance

This is a bounded, guided use of the internal v0.2.2 plugin in a real project.
The coordinator already knew the project and wrote the task. It is neither a
blind evaluation nor a measured efficiency comparison. Private transcripts,
account data and generated application artifacts are not included here.

## What was observed

The Linux worker loaded the packaged project-wiki Skill and its collaboration
reference, invoked the actual native task index and selected feature/impact views,
read feature prose/graphs and the design brief, then produced source changes.
Its first run reached a successful terminal result and stopped. It returned a
receipt distinguishing local preview, account persistence, native clients,
mechanism tests, offline images and actual runtime acceptance. The coordinator
inspected real source files and offline rendered images, rather than treating
the terminal status or receipt as completion.

This source baseline used an older native router without workflow metadata. The
plugin's not_declared result was truthful; task instructions linked the native
protocol separately. A different, earlier read-only trial exercised the optional
native-workflow transport. These are different observations, not interchangeable
proof of native adapter adoption.

The first packet had incorrect existing-locale paths and a test extension that
the repository would not discover. Missing-file impact records did not prove
that those guessed paths were right. The worker found the real paths in the
project and requested a scope amendment. The coordinator explicitly approved
those paths and preserved the original packet. The worker also identified that
the initial no-contract-change limit conflicted with the repository's required
feature-audience gate. The approved amendment allowed an additive existing flag
registry/contract entry instead of a parallel account predicate. Actual tool
output showed the worker read the approval and changed the source accordingly.

After the first run was confirmed terminal, the coordinator archived all 30
changed/new source paths and hashes, captured a new packet from the actual file
set, and resumed the same worker with concrete visual/interaction feedback.
That second implementation run was still active at this checkpoint. The initial
packet was not rewritten retroactively to pretend it covered the broader scope.

## Acceptance differences that mattered

The first offline images showed recognizable variants, but the selected animal
was too small in the narrow viewport and the flat scene missed the intended
contained-world emergence. The coordinator kept visual acceptance open and sent
those concrete failures back for implementation. Mechanism and static-render
checks could not establish live gesture, animation continuity, account collection
or native-client acceptance. A packet capability must describe the intended user
result; it cannot shrink to whichever implementation is easiest to test.

A separate live project CI failure exposed a return-path gap: the canonical wiki
finish command regenerated the main relation graph, while a required local
reading projection stayed stale. The independent final static gate rejected it.
The native candidate now invokes its existing projector in the same finish path,
after its canonical graph and before navigation generation. No global read rule,
second relation inventory, gate exemption or plugin-specific project command was
added. The original CI failure remains evidence; final exact-head CI was pending.

## What this does not prove

- Complete start/delegate/finish/recovery closure: final-diff reconciliation and
  the resumed implementation/runtime review remain pending.
- Independent semantic correctness, desktop GUI discovery, trusted lifecycle
  hooks, model coordination by the plugin, or measured time savings.
- Main or production adoption of the project's candidates, native rendering,
  persistent identity/collection, or release acceptance.

## Follow-up cases for the existing evaluation suite

1. A missing planned path can mean an intentional new file or a wrong existing
   filename. Ask the native project route/source for the distinction; do not
   silently replace paths or count an empty impact record as reviewed.
2. An actual file/scope expansion preserves the original packet and requires an
   explicit owner decision plus a fresh actual-diff capture for reconciliation.
3. A quoted canonical finish command is a declaration, not proof of complete
   generation or execution. Use the real downstream freshness result to repair
   the native return path rather than adding unrelated mandatory reads.
4. A successful worker result with useful code and offline pictures can still
   fail the requested visual or interaction outcome. Preserve that failure and
   return an actionable revision without marking the feature complete.

These are candidate evaluation cases, not additional implemented automated tests
or new host enforcement. Keep actual measured results separate from this list.
